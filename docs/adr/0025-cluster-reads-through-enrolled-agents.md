# Cluster Reads Arrive Through Enrolled Agents, Never Stored Credentials

Atlas will not store cluster credentials in the control plane and will not initiate connections into cluster networks. (Scope note, 2026-08-20: this rule governs the Ceph cluster trust domain only — third-party observability integrations are pull, per ADR-0027.) An Operator registers a Cluster in Atlas and receives enrollment instructions; an Atlas Agent deployed in the cluster's trust domain enrolls using a registration credential, then collects cluster state (over the Ceph Dashboard REST API per ADR-0023, with credentials configured at deploy time and never sent to Atlas) and pushes observations to Atlas over an outbound connection. Security posture drove this over the simpler pull model: a compromised control plane yields no cluster credentials and no inbound network path into cluster networks, credential custody stays in the cluster's trust domain, and there is no stored-credential pattern that could later quietly extend from read-only to write credentials. It is also an adoption requirement: Atlas's first target deployment operates in a highly secure environment where a control plane that stores cluster credentials or initiates connections into cluster networks would be disqualifying.

This is the Rancher-style architecture: control plane deployed by the operator, cluster defined in the UI/API, agent registered from inside the cluster dialing out. It is also the strategic end-state anyway — v0.0.10 mutation requires an enrolled agent (ADR-0003), so Atlas grows one agent identity and one channel, read-first, rather than building a pull path it would later retire.

**Considered options**: pull with encrypted, read-only Dashboard credentials stored in Atlas (the industry-standard control-plane posture — Prometheus, NetBox, Grafana; seriously considered and recommended before rejection: a long-lived secret at rest, inbound firewall openings into cluster networks, and a pattern that invites extending to write credentials); a static Dashboard token (rejected in ADR-0023 — expires, stranding unattended runs); building the full mutation-capable agent immediately (rejected — the v0.0.9 safety chain must precede mutation).

**Consequences**

- Supersedes ADR-0023's credential-custody consequence ("Atlas holds a long-lived Dashboard credential in environment configuration") and its control-plane sync framing; the Dashboard REST reading approach itself survives, relocated into the Agent.
- `ATLAS_READ_SOURCE=ceph` (live direct reads, deferred in ADR-0023) will never ship. The PostgreSQL read model is the only real-cluster read path; the API always serves from synced observations (ADR-0014), so `ATLAS_READ_SOURCE` stays `provider | postgres`.
- The existing `ATLAS_PROVIDER_MODE=ceph` control-plane pull path (env-var Dashboard credentials) must be removed when the agent path replaces it; the no-stored-credentials posture is not optional per environment.
- v0.0.8 re-scopes around Cluster Registration, Enrollment, and a read-only Agent push path. The v0.0.8 Agent carries no command channel at all — operation dispatch joins the same enrolled identity in v0.0.10.
- Enrollment mechanism (registration credential shape, certificate authority, revocation, re-enrollment) is a companion decision recorded separately.
